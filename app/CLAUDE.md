## Admin panel

- URL: `/admin` on either deployment.
- Single shared password (no username) — stored ONLY as a Cloudflare secret
  (`ADMIN_PASSWORD`), never in code or in this file. Rotate/view via
  `npx wrangler secret put ADMIN_PASSWORD` (put-only, can't be read back) or
  ask the owner.
- Session sealing key: `ADMIN_SESSION_SECRET` (also a Cloudflare secret, 32+
  random chars, never needs to be typed by a human).
- Lets the owner: view/mark-done reservations, add/edit/delete menu items.
  Reservations have no delete button by design (only a status toggle) — the
  DB read CLI (`higgsfield website db`) is read-only anyway.

## Architecture gotchas (already fixed once — don't reintroduce)

- **Secrets/bindings come from `bindings()` in `src/lib/bindings.server.ts`,
  never from `process.env`.** This platform (and Cloudflare Workers
  generally) exposes D1/R2/KV *and* custom secrets/vars through the same
  `cloudflare:workers` `env` object — `process.env` is empty for anything set
  via `wrangler secret put` / `higgsfield website secrets set`. Getting this
  wrong is exactly why `/admin` 500'd in production the first time.
- `bindings.server.ts` resolves that `env` via a **dynamic** `import()`
  wrapped in try/catch, not a static one — a static import throws at
  module-link time when `cloudflare:workers` doesn't exist (plain
  `bun run dev`/`vite dev`, which runs in Node), which used to crash the
  *entire* page the instant any route loader touched a D1-backed function.
  Keep it dynamic.
- **Local `bun run dev` cannot exercise real D1 reads/writes** — bindings only
  exist in an actual deployed Worker. Every D1-backed function must degrade
  gracefully when `!DB` (return `[]`/defaults, don't throw) so local dev of
  the rest of the site still works.
- The public menu (`Menu` component in `src/routes/index.tsx`) reads from D1
  via `getMenu()` in a route loader — it is NOT hardcoded anymore. The admin
  panel edits the same table.
- CSP (`src/lib/security-headers.server.ts`) must keep `blob:` in `media-src`
  — the scroll-scrub video player sources `<video>` from `URL.createObjectURL`,
  and Chrome silently rejects that without it (this was the actual root cause
  of the "video won't play on mobile" bug, not a mobile-specific issue at all).
